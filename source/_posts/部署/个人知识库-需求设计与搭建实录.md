# 上篇 · 需求设计

## 1. 背景与目标

搭建一个个人知识库，承载两类内容：**技术学习笔记**与**业界内容洞察**。

核心诉求（按优先级）：

1. **快速**：丢链接 / 粘文字 / 扔 PDF，都能快速变成合格的知识库文档
2. **高质量**：内容准确、有出处、结构统一
3. **合心意**：通过"风格学习循环"让 AI 逐步学会使用者的偏好，后期一步到位
4. **不绑死**：不依赖特定 AI 应用，通过可配置的 API 调用，模型可自由切换

## 2. 总体架构

```
        写入侧（生产线）                    读取侧（消费线）
┌───────────────────────────┐      ┌───────────────────────────┐
│ kb ingest / learn / check │      │  Hexo + NexT 静态博客      │
│ skill 包（SKILL.md+规则）   │      │  分类/归档+本地搜索+词条跳转│
│ 模型 API（OpenAI 兼容）    │      │  体检按钮 / 报告页          │
└─────────────┬─────────────┘      └─────────────▲─────────────┘
              │ 读写                              │ 只读
              ▼                                   │
┌─────────────────────────────────────────────────────┐
│  GitHub 仓库 · 内容层（唯一事实来源，纯 Markdown）      │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐  │
│  │ 第1层        │  │ 第2层        │  │ 第3层        │  │
│  │ 原始资料     │  │ 词条库       │  │ 规则文件     │  │
│  │ sources/    │  │ source/     │  │ skill/rules/│  │
│  │ （只读）     │  │ _posts/tech │  │ （宪法+风格） │  │
│  │             │  │ _posts/ins… │  │             │  │
│  └─────────────┘  └─────────────┘  └─────────────┘  │
└─────────────────────────────────────────────────────┘
         │  推代码触发 GitHub Actions 自动构建
         ▼
  GitHub Pages 发布
```

**架构原则：读写分离。** 写入侧（skill + 脚本 + 模型 API）与读取侧（Hexo 网站）互不依赖，两侧都只依赖内容文件和规则文件：

- 网站构建只读 `source/` 内容目录，不感知 AI、API、脚本的存在——删掉整个写入侧，网站照常构建
- 写入侧不感知网站的存在——按规则文件操作 Markdown，写完推代码即自动触发构建
- 由此获得双侧可替换性：展示方案（Hexo/MkDocs/Obsidian/其他）和生产线（模型/skill 平台）各自独立演进
- **仓库策略**：初期单仓库 + 目录级隔离；日后可平滑拆分为内容仓库 + 工具仓库，届时内容层无需任何改动

### 关键决策

| 决策点 | 结论 |
|---|---|
| 载体 | 复用现有 Hexo 博客仓库（本地 `D:\wiki`，Hexo 8 + NexT 主题），发布到 GitHub Pages |
| 词条链接 | 标准 Markdown 链接（仓库内直接可用；网站上经链接转换插件生效） |
| 词条写入 | AI 直接写入，含自动合并/更新已有词条的权限 |
| 回答规矩 | 务实派：优先库内资料；库外知识可用，但必须标注"来自库外" |
| 内容分区 | `source/_posts/tech/`（技术笔记）与 `source/_posts/insights/`（业界洞察），Hexo 按子目录自动归类，允许跨区互链 |
| 体检方式 | 网站上放"体检"按钮，触发 GitHub Actions 后台执行；语义检查默认关闭，手动开启 |
| 生成方式 | 模型 API（OpenAI 兼容接口）可配置切换，首个接入 Kimi；使用入口为 agent 对话 / 本地网页对话 / GitHub Issue，CLI 仅作底层管道 |
| 仓库可见性 | 公开（顺带获得免费 GitHub Pages 发布） |

### 单仓库目录结构

```
仓库根/（D:\wiki）
├── sources/            # 第1层：原始资料（全文存档 + 摘录卡）——Hexo 不渲染此目录
├── source/
│   └── _posts/
│       ├── tech/       # 第2层：技术笔记词条（Hexo 自动归类为 tech）
│       └── insights/   # 第2层：业界洞察词条（Hexo 自动归类为 insights）
├── skill/              # 第3层 + 生产线——Hexo 不渲染此目录
│   ├── SKILL.md
│   ├── rules/          # constitution.md + style-profile.md
│   └── scripts/        # 工具源码：CLI + 网页对话界面 + 体检
├── _config.yml         # Hexo 站点配置
├── _config.next.yml    # NexT 主题配置
├── package.json        # Hexo 依赖
└── .github/workflows/  # 自动构建发布 + 体检按钮 + Issue 触发入库
```

不进仓库的三样东西：

- **API key**：本地 `config.yaml` 被 git 忽略；Actions 用的那份存仓库 Secrets，永不入代码
- **网站成品**：Pages 发布的是构建产物（HTML），由 Actions 生成，主分支只有 Markdown 源码
- **第三方依赖**：构建时按依赖清单自动安装，不进仓库

## 3. 第 1 层：原始资料层（sources/）

**规矩：只读，一个字不改。本层的目的是"可溯源"，不是"全文收藏"——引用的内容能逐字对应到不可篡改的存档、能找回原始出处即可。**

只读层分两种存档形态，按入库入口区分。

### 3.1 全文存档（资料驱动入口专用）

用户主动投喂的资料（链接/文字/PDF），原样全文保存：

- 每份资料在文件头部记录元数据：标题、来源链接（如有）、收录日期、资料类型（链接/文字/文件）、用户备注（可选）
- 网页类资料保存正文全文（不依赖原链接存活，防止日后失效）
- PDF 等二进制文件原样存放，另存一份提取出的纯文本供 AI 读取
- 命名规范：`YYYY-MM-DD-资料标题.md`，禁止覆盖已有文件；同名冲突时追加序号

### 3.2 摘录卡（研究入库入口专用）

AI 检索收集的资料**不存全文**，只为词条实际引用的内容建立"摘录卡"：

- 摘录卡内容：被引用的**原文片段逐字摘录**（一个字不改）+ 元数据（来源标题、原链接、收录日期、片段在原文中的位置/上下文、资料类型标注"AI 检索收集"）
- 命名规范：`YYYY-MM-DD-主题-序号.md`
- **去重**：同一来源已被收录过时，复用已有卡片，只追加新摘录，不重复存档
- 原链接失效不影响库内可用性——引用文字已在卡内
- 配置开关：`研究模式是否保留全文`，默认关闭

## 4. 第 2 层：词条层

### 4.1 词条模板（固定结构，供 AI 和脚本解析）

```markdown
# 词条名

> 一句话摘要（这个词条讲什么）

## 核心内容

（正文，可含小节、代码块、表格；直接引用原文的句子句尾标来源编号 [1]）

## 关联词条

- [相关词条A](../路径/a.md) — 关联原因一句话
（允许为空，但区块标题必须保留）

## 出处

- [1] 原始资料标题，`sources/2026-xx-xx-xxx.md`，收录日期，原链接
```

### 4.2 入库流程（新资料进来时 AI 的处理顺序）

1. 读取第 3 层规则文件和风格档案
2. 将原始资料存入 `sources/`（只读层；资料驱动入口存全文，研究入库入口建摘录卡）
3. **先查重**：检索现有词条，判断本次操作类型：
   - **新建**：内容是全新主题 → 创建新词条
   - **合并**：与已有词条高度重合 → 并入该词条，补充出处
   - **更新**：已有词条存在但信息过时/不完整 → 修订该词条，保留修订痕迹
4. 写入/更新词条，维护"关联词条"双向关系（A 链 B 时检查 B 是否应回链 A）
5. 更新索引（分类/标签），保证网站导航同步
6. 输出本次操作摘要：新建了哪些、合并了哪些、更新了哪些

### 4.3 两种入库触发方式

知识库支持"资料驱动"和"问题驱动"两种入口，最终都汇入同一条标准入库流程（4.2），**词条必须建立在 sources/ 层的真实存档上，不允许 AI 凭空生成词条**。

**方式一 · 资料驱动（用户喂资料）**：即 4.2 的标准流程，资料来自用户提供的链接/文字/文件。

**方式二 · 问题驱动（研究入库）**：用户只有一个想了解的概念或问题，没有现成资料：

1. **先答**：AI 直接回答问题，按务实派规矩标注"⚠️ 此条来自库外，未入库"
2. **再问**：回答末尾询问"要不要入库？"
3. **再存**：用户确认后，AI 主动检索收集 2~5 篇真实资料，按 3.2 节建立**摘录卡**（不存全文），再走 4.2 标准流程生成词条、出处指向摘录卡
4. 词条内容**以收集到的真实资料为准**，不直接采用第 1 步的回答文本——避免模型记忆/幻觉直接进入知识库

### 4.4 防膨胀与防重复机制

- 查重是强制前置步骤，不是可选项
- "合并/更新"优先于"新建"：规则文件明确规定——*能用已有词条承载的内容，不允许新建词条*
- 体检中的"近义词条"检查作为兜底，定期发现漏网的重复

### 4.5 回答问题的规矩（务实派）

- 优先引用库内词条和原始资料，引用处标注来源
- 库内没有覆盖的问题，明确说"库里没有相关内容"
- 使用库外知识时，标注"⚠️ 此条来自库外，未入库"

### 4.6 存量旧文处理原则

现有 Hexo 仓库中复用的是"壳"（框架、主题、部署链路），**不是旧内容**。旧博客文章不自动纳入词条体系、不强制套用词条模板：

- **保持原样**：旧文继续留在 `source/_posts/` 正常显示，它们不是"词条"，只是博客旧文
- **想翻新的**：由用户挑选，旧文作为"原始资料"重新走 `ingest` 流程，按新模板与风格档案生成规范词条，旧文随后删除或移出；这批翻新同时作为风格学习循环的第一批练习素材
- **看不上眼的**：直接删除
- 过渡期内新体系词条与旧博客文并存，随翻新进度此消彼长

## 5. 第 3 层：规则文件 + Skill 封装

第 3 层不是两份"散养"的文档，而是封装成一个**标准 skill 包**（遵循 SKILL.md 规范）。这样规则、风格、操作流程不依赖任何特定 AI 应用的注入逻辑——任何支持 skill 的 agent 平台（Kimi、Claude Code、Codex 等）加载它就知道如何维护这个知识库。

### 5.1 skill 包结构

```
skill/
├── SKILL.md            # 入口：知识库是什么、核心工作流（入库/研究学习/问答/体检）怎么执行
├── rules/
│   ├── constitution.md   # 组织宪法（见 5.2）
│   └── style-profile.md  # 风格档案（见 5.3）
└── scripts/              # 机械操作的辅助脚本
```

- **SKILL.md**：面向 AI 的操作手册。说明三层架构，定义入库（查重→新建/合并/更新）、研究学习（先答→再问→检索收集→入库）、带规矩问答、体检四个工作流的执行步骤，并指引 AI 在生成内容前必读 `style-profile.md`
- **可移植性**：换平台、换模型时，只要把这个 skill 目录加载进去，知识库的"玩法"原样生效；模型本身只需是 OpenAI 兼容接口
- **兜底**：对于不支持 skill 的纯 API 调用场景，CLI 工具会把 `SKILL.md + constitution.md + style-profile.md` 拼接注入 system prompt，两种路径读的是同一套规则，不存在两套规矩漂移的问题

### 5.2 constitution.md（组织宪法，相对稳定）

- 三层架构及各层规矩（原始层只读、词条模板、出处格式）
- 入库流程（查重 → 新建/合并/更新的判断标准）
- 目录与命名规范
- 回答问题的规矩（务实派条款）
- 体检标准

### 5.3 style-profile.md（风格档案，持续演化）

记录用户的写作偏好，由"风格学习循环"维护：

1. AI 生成词条 → 用户人工修改
2. AI 对比"原版 vs 修改版"，归纳差异（如：偏好短句/长句、要不要保留代码示例、摘要写法、详略程度）
3. 差异追加进 `style-profile.md`，附示例
4. 后续生成时先读风格档案，逐步逼近"一步到位"

## 6. 工具链与使用入口

本地 Python 工具，作为 skill 包内的 `scripts/` 交付，**不绑定任何特定 AI 应用**。

### 6.1 使用入口（日常接触面，按优先级）

| 入口 | 形态 | 适用场景 |
|---|---|---|
| ① agent 平台（如 Kimi Work） | 对话式，加载 skill 包后直接聊天操作本地仓库 | 电脑上，体验最好；收资料、学概念、问答、体检全支持 |
| ② 本地网页对话（`kb web` 启动） | 浏览器打开聊天页面：左侧对话，右侧可预览知识库文件；粘贴链接、提问、确认入库全在页面里完成 | 不想打开 AI 应用时使用；功能与入口①等价 |
| ③ GitHub Issue 触发 | 手机/任意设备打开仓库网页，新建 Issue 粘贴链接；Actions 后台入库并在 Issue 下回复结果 | 手机端随手收资料（异步，几分钟完成；不支持来回追问的"学概念"流程） |
| 兜底 · 命令行 | `kb` 命令直接调模型 API | 脚本自动化；也是入口②③的内部实现管道，日常无需直接使用 |

阅读入口不分场景：任何时候打开 GitHub Pages 网站即可。

**输入网页与查看网页是两个不同的网站**（读写分离的直接体现）：

- 查看网页 = GitHub Pages 静态站：只读、全天候、任何设备可看
- 输入网页 = 本地 `localhost` 页面：仅在电脑上启动时存在；必须本地运行的两个原因——要写文件/提交 git、API key 不能暴露在任何托管网页中
- 衔接：输入网页右侧自带知识库浏览栏，"边聊边看"单页闭环；顶部放"查看已发布网站"跳转链接
- 远期可选项：整套系统部署到自有服务器后，查看与对话可合并为同一站点，属后期升级项

### 6.2 配置（config.yaml）

```yaml
llm:
  base_url: "https://api.moonshot.cn/v1"    # 任意 OpenAI 兼容接口，首个接入 Kimi
  api_key: "sk-..."
  model: "model-name"                        # 换模型只改这一行
ingest:
  research_keep_fulltext: false              # 研究入库是否保留全文（默认仅建摘录卡）
  research_max_sources: 5                    # 研究入库单次最多收集几篇资料
```

### 6.3 功能命令（底层管道）

| 命令 | 作用 |
|---|---|
| `web` | 启动本地网页对话界面（入口②），浏览器自动打开聊天页 |
| `ingest <链接/文件/文本>` | 入库：存档原始资料 → 查重 → 生成/合并/更新词条 |
| `learn <主题/问题>` | 研究入库：先回答 → 确认后检索收集真实资料 → 走标准入库流程 |
| `check` | 体检（本地版）：机械检查 + 可选语义检查 |
| `ask "<问题>"` | 带规矩检索库内内容并回答 |

网页对话界面要求：

- 聊天式交互，支持"先答→再问→确认入库"的多轮流程
- 对话中可直接粘贴链接/文字/上传文件，等价于触发 ingest
- 侧边栏可浏览知识库目录与词条内容，入库结果即时可见
- 纯本地运行（localhost），不经过第三方服务器

### 6.4 体检的两个阶段

- **阶段一 · 机械检查**（纯脚本，不耗 API）：死链、孤儿词条、无出处内容、过期内容
- **阶段二 · 语义检查**（调用模型 API，有费用；**默认关闭**，`check --deep` 手动开启）：近义词条识别与合并建议、风格一致性抽查

### 6.5 网页体检按钮

- 网站页面上放置"运行体检"按钮 → 实际触发 GitHub Actions（workflow_dispatch）
- 后台跑 `check`，结果生成为"体检报告"页面发布到网站
- 报告含：问题清单、位置、建议操作；语义类建议（合并词条）只给建议不自动执行，由用户确认

## 7. 技术选型

| 组件 | 选型 | 理由 |
|---|---|---|
| 存储 | GitHub 公开仓库 | 版本管理、随处可访问、免费 |
| 静态站点 | Hexo 8 + NexT 主题（复用现有博客） | 已部署、使用者熟悉；分类/归档/本地搜索能力齐备 |
| 链接转换 | Hexo 插件将词条内 `.md` 相对链接转为站点 URL | 保证词条互链在仓库和网站上双端可用 |
| 自动发布 | GitHub Actions → GitHub Pages | 推内容即更新网站，零运维 |
| 体检后端 | GitHub Actions + 模型 API（密钥存 Actions Secrets） | 静态站无法跑 AI，用 Actions 做后台执行 |
| 生成工具 | Python（OpenAI 兼容 SDK）+ 本地网页对话界面 | 模型可切换，不绑定特定 AI 应用；日常以网页对话为主，CLI 为底层管道 |

## 8. 非目标（本阶段不做）

- 不做 Obsidian 双链语法（用标准 Markdown 链接替代，反链靠体检统计）
- 不做多人协作、权限管理
- 不做移动端 App
- 不做规模预设与容量规划（规模大了再演进目录结构）
- 体检报告不自动执行合并等破坏性操作，仅提供建议

# 下篇 · 底座搭建实操（Hexo + NexT + GitHub Pages）

读取侧底座使用 Hexo 将 Markdown 文件编译为静态网页，通过 GitHub Pages 托管，并借助 GitHub Actions 实现 push 自动部署。

涉及的组件：

| 组件 | 说明 |
|------|------|
| Hexo | 基于 Node.js 的静态博客框架，负责将 Markdown 编译为静态站点 |
| NexT | Hexo 生态中使用最广泛的社区主题，提供多种方案和丰富的可配置项 |
| GitHub Pages | GitHub 提供的静态网站托管服务，无需自建服务器 |
| GitHub Actions | CI/CD 流水线，用于在代码推送到仓库后自动执行编译和部署 |

## 10. 环境准备

### Node.js

Hexo 基于 Node.js，要求版本不低于 v18。执行以下命令确认已安装：

```bash
node --version
```

未安装时前往 [Node.js 官网](https://nodejs.org/) 下载 LTS 版本。

### Git

用于版本控制和远程推送：

```bash
git --version
```

未安装时前往 [Git 官网](https://git-scm.com/) 下载。

### GitHub 账号

用于代码托管和静态站点发布。如需在命令行中操作 GitHub，可安装 [GitHub CLI](https://cli.github.com/)（可选，不影响后续步骤）。

## 11. 安装 Hexo

在终端（Windows 推荐 Git Bash 或 PowerShell）中执行：

```bash
npm install -g hexo-cli
```

安装完成后验证：

```bash
hexo version
```

## 12. 初始化项目

```bash
mkdir D:\wiki
cd D:\wiki
hexo init .
npm install
```

`hexo init .` 会在当前目录生成项目结构：

```text

├── _config.yml          # 站点配置文件

│   └── _posts/          # 文章目录

```

## 13. 安装 NexT 主题

NexT 是 Hexo 社区中安装量最高的主题，特点为功能完善、文档齐全、可配置程度高。

```bash
npm install hexo-theme-next
```

安装后修改 `_config.yml` 中的 `theme` 字段，将默认值 `landscape` 替换为 `next`：

```yaml
theme: next
```

## 14. 配置站点信息

编辑项目根目录下的 `_config.yml`，重点修改以下字段：

```yaml
title: 个人学习 Wiki
subtitle: 日拱一卒，功不唐捐
description: 个人学习知识库
author: 你的名称
language: zh-CN
timezone: 'Asia/Shanghai'

theme: next
```

`url` 字段填写最终部署地址，GitHub 仓库创建后即可确定。

## 15. 配置 NexT 主题

NexT 的主题配置位于项目根目录下的 `_config.next.yml`。若该文件不存在，手动新建。

### Scheme 选择

NexT 提供四种方案，通过 `scheme` 字段切换：

| 方案 | 说明 |
|------|------|
| Muse | 无侧边栏，全宽布局 |
| Mist | 紧凑型侧边栏 |
| Pisces | 常规侧边栏，适合知识库 |
| Gemini | 大尺寸侧边栏 |

推荐 Pisces。基础配置：

```yaml
scheme: Pisces

darkmode: true

menu:
  home: / || fa fa-home
  categories: /categories/ || fa fa-th
  about: /about/ || fa fa-user

sidebar:
  position: left
  display: post

back2top:
  enable: true
  sidebar: false
  scrollpercent: false

codeblock:
  copy_button:
    enable: true
    show_result: true
    style: flat

excerpt_description: true
```

- `darkmode: true` — 启用暗黑模式切换
- `excerpt_description: true` — 首页使用 `description` 字段作为摘要，而非截取正文

## 16. 本地预览

推送至远程仓库之前，先在本地启动服务验证效果：

```bash
hexo server
```

或简写为 `hexo s`。默认访问地址为 `http://localhost:4000`。若端口被占用，Hexo 会自动切换到下一个可用端口，注意观察终端输出的实际地址。

`hexo server` 会持续监听文件变更，修改文章或配置后刷新浏览器即可查看更新，无需手动重启。按 `Ctrl + C` 停止服务。

## 17. 创建 GitHub 仓库

在 GitHub 上新建仓库，名称建议为 `wiki`（该名称将作为 URL 路径的一部分，如 `用户名.github.io/wiki`）。

仓库可见性需设为 **Public**，这是使用免费 GitHub Pages 的前提。

若已安装 GitHub CLI：

```bash
gh repo create 你的用户名/wiki --public --description "个人学习 wiki 知识库"
```

## 18. 配置自动部署

GitHub Actions 可以将编译部署自动化：向 `main` 分支推送代码后，自动触发编译并部署至 `gh-pages` 分支。

在项目目录下创建 `.github/workflows/deploy.yml`：

```yaml
name: Deploy
on:
  push:
    branches: [main]

permissions:
  contents: write

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '20'

      - run: npm ci

      - run: npx hexo generate

      - uses: peaceiris/actions-gh-pages@v4
        with:
          github_token: ${{ secrets.GITHUB_TOKEN }}
          publish_dir: ./public
          publish_branch: gh-pages
          force_orphan: true
```

工作流说明：

1. `actions/checkout@v4` — 检出仓库代码
2. `actions/setup-node@v4` — 配置 Node.js 环境
3. `npm ci` — 安装依赖
4. `npx hexo generate` — 编译生成静态文件至 `public/` 目录
5. `peaceiris/actions-gh-pages@v4` — 将 `public/` 目录推送至 `gh-pages` 分支

## 19. 推送并启用 Pages

```bash
cd D:\wiki
git init
git checkout -b main
git add -A
git commit -m "初始化 wiki"
git remote add origin git@github.com:你的用户名/wiki.git
git push -u origin main
```

> 使用 `git@github.com:...` 格式的 SSH 地址需要先在 GitHub 中配置 SSH 公钥。也可使用 HTTPS 地址 `https://github.com/你的用户名/wiki.git`，首次推送时会提示登录。

推送完成后，进入 GitHub 仓库页面 → Settings → Pages，将 Source 设置为 `gh-pages` 分支。GitHub 将在数分钟内完成首次部署。

最终访问地址：`https://你的用户名.github.io/wiki`

此后每次向 `main` 分支推送代码，GitHub Actions 均会自动重新部署。

## 20. 日常写作与维护

### 日常写作流程

```bash
cd D:\wiki

# 1. 创建新文章
hexo new "文章标题"

# 2. 文章生成于 source/_posts/ 目录，使用任意文本编辑器编辑

# 3. 本地预览
hexo server
# 浏览器访问 http://localhost:4000

# 4. 推送
git add -A
git commit -m "新增：文章标题"
git push
```

> 待 M2 入库闭环上线后，词条类内容由 `ingest`/`learn` 流程自动生成，`hexo new` 仅用于非词条的传统博文。

### 手动编译

若需查看编译产物或在离线状态下调试：

```bash
hexo clean       # 清除缓存与编译输出
hexo generate    # 重新编译至 public/ 目录
```

`hexo clean` 仅在配置变更未生效或编译异常时使用。日常预览使用 `hexo server` 即可，该命令已内置编译步骤。

## 21. 文章编写规范

### 文件格式

所有文章置于 `source/_posts/` 目录，文件格式为 Markdown（`.md`）。词条按分区置于 `source/_posts/tech/` 与 `source/_posts/insights/` 子目录，Hexo 按子目录自动归类。

### Frontmatter

每篇文章以 YAML 格式的 Frontmatter 开头，定义元信息：

```yaml
---
title: 文章标题
date: 2026-06-08 12:00:00
categories: [一级分类, 子分类]
description: 文章概述，显示于首页标题下方，建议控制在两句话以内。
---
```

`description` 决定了首页文章卡片的概述文字。若省略此字段，Hexo 将自动截取正文头部内容作为摘要（通常效果不佳），因此建议每篇文章自行填写。

### 文章模板

`hexo new` 命令使用 `scaffolds/post.md` 作为模板生成文件。可编辑该模板，预设常用的 categories，减少重复填写。

## 22. Windows 环境注意事项

- 终端推荐使用 **Git Bash** 或 **PowerShell**
- 文件路径中的正斜杠 `/` 和反斜杠 `\` 均可使用，Hexo 内部统一处理
- `node_modules/` 由 `.gitignore` 排除，不会被提交至仓库
- 如 `hexo server` 启动异常，先执行 `hexo clean` 清空缓存后重试
